  <action>
Modify the `streamBedrockToSSE` function in `server/src/services/bedrock.ts` to accept a `loreContext` parameter and inject it as a second SystemContentBlock in the ConverseStreamCommand.

**IMPORTANT:** Phase 4 creates this file. Read it first to understand the current signature. Phase 4 research defines the signature as `streamBedrockToSSE(messages, systemPrompt, res, signal)`. This task changes the signature to accept lore context.

**Changes to make:**

1. Change the `streamBedrockToSSE` function signature to add `loreContext: string` as the third parameter (after `systemPrompt`, before `res`):
   ```typescript
   export async function streamBedrockToSSE(
     messages: BedrockMessage[],
     systemPrompt: string,
     loreContext: string,
     res: Response,
     signal: AbortSignal,
   ): Promise<string>
   ```

2. Inside the function, build the system blocks array dynamically:
   ```typescript
   const systemBlocks: Array<{ text: string }> = [{ text: systemPrompt }];
   if (loreContext) {
     systemBlocks.push({ text: loreContext });
   }
   ```

3. Pass `systemBlocks` to the ConverseStreamCommand instead of `[{ text: systemPrompt }]`:
   ```typescript
   const command = new ConverseStreamCommand({
     modelId: config.BEDROCK_MODEL_ID,
     system: systemBlocks,
     messages,
     inferenceConfig: { maxTokens: 1024, temperature: 0.85 },
   });
   ```

4. Do NOT change the BedrockRuntimeClient singleton, the stream iteration logic, or the `res.write()` SSE pattern. Only the system prompt assembly changes.

**Why second SystemContentBlock (not concatenation):** Claude processes separate system blocks as distinct instructions. Lore context as a separate block keeps the base DM persona cleanly separated from the contextual lore injection. This prevents prompt confusion where lore attributes might be misinterpreted as DM behavior instructions.
