<objective>
Optimize Redis round-trips in conversation store (criterion 8), add SSE backpressure handling (criterion 7), and add mutex protection to in-memory conversation fallback (criterion 16).

Purpose: The chat route currently makes 8+ Redis round-trips per turn (getOrCreate + appendMessage(user) + getWindowedHistory + appendMessage(assistant), each doing GET+EXPIRE). GETEX halves read round-trips, and the local variable pattern reduces writes. SSE backpressure prevents Node.js from buffering unbounded data when slow clients can't keep up. The in-memory fallback store has race conditions under concurrent access without locking.

Output: Optimized conversation store with GETEX, reduced writes, mutex-protected in-memory fallback, and backpressure-aware SSE streaming.
</objective>

  <name>Task 1: GETEX optimization + withLock on in-memory fallback</name>
  <files>server/src/services/conversationStore.ts</files>
  <action>
    1. In `_getFromRedis`:
       - Replace the two-call pattern (GET + EXPIRE) with a single GETEX call:
         ```typescript
         private async _getFromRedis(conversationId: string): Promise<Conversation | null> {
           const raw = await redisClient.getEx(redisKey(conversationId), {
             EX: CONVERSATION_TTL_SECONDS,
           });
           if (!raw) return null;
           return JSON.parse(raw) as Conversation;
         }
         ```
       - This combines GET + TTL refresh into one Redis round-trip (requires Redis 6.2+).
       - Remove the separate `await redisClient.expire(...)` call.

    2. Wrap GETEX in a try/catch to handle Redis versions that don't support GETEX:
       - If the command throws (e.g., "ERR unknown command"), fall back to the old GET+EXPIRE pattern.
       - Log a one-time warning: `logEvent("warn", "conversationStore.getex_unsupported", { fallback: "get+expire" })`.
       - Use a module-level flag `let getexSupported = true;` that flips to false on first failure, so subsequent reads go directly to GET+EXPIRE without retrying GETEX.

    3. Add mutex/lock protection to the in-memory conversation fallback (criterion 16):
       - Install `async-mutex` or implement a simple promise-based lock keyed by conversationId.
       - Simplest approach — a Map of per-conversation locks:
         ```typescript
         const conversationLocks = new Map<string, Promise<void>>();

         async function withLock<T>(key: string, fn: () => Promise<T>): Promise<T> {
           // Wait for any existing operation on this key
           while (conversationLocks.has(key)) {
             await conversationLocks.get(key);
           }
           let resolve: () => void;
           const lock = new Promise<void>(r => { resolve = r; });
           conversationLocks.set(key, lock);
           try {
             return await fn();
           } finally {
             conversationLocks.delete(key);
             resolve!();
           }
         }
         ```
       - Wrap the in-memory fallback paths in `getOrCreate` and `appendMessage` with `withLock(conversationId, async () => { ... })`.
       - This prevents race conditions where two concurrent requests for the same conversationId read stale data from the in-memory Map (e.g., both read history length 5, both append, result is history length 6 instead of 7).
       - Only apply withLock to the in-memory fallback path (when Redis is unavailable). Redis operations are already atomic per-command.

    NOTE: This plan depends on Plan 18-01 which adds userId to the conversation type and getOrCreate signature. The GETEX and withLock changes are compatible with the userId additions.

    1. SSE Backpressure in `chat.ts`:
       - After the SSE headers are written, create a helper function for checked writes:
         ```typescript
         function checkedWrite(data: unknown): boolean {
           if (clientDisconnected) return false;
           return res.write(`data: ${JSON.stringify(data)}\n\n`);
         }
         ```
       - In the `createMoodStreamDetector` callbacks, replace direct `res.write` with `checkedWrite`.
       - For the text callback, check the return value. If `false` (backpressure), log it but continue (conservative approach — don't make the callback async to avoid breaking the moodStreamDetector sync callback chain). The Bedrock stream is short-lived (seconds) and the kernel TCP buffer handles temporary backup.
       - Log when backpressure is detected: `logEvent("warn", "chat.sse_backpressure", { conversationId: conversation.id })`.
       - This satisfies criterion 7's requirement to "check res.write() return" without the risky async callback refactor described in the research pitfall #3.

    2. Local conversation variable pattern:
       - After `getOrCreate`, the conversation is already a local variable. The current code calls `appendMessage(conversation.id, ...)` which does a full Redis read+write each time.
       - Refactor the chat route to minimize Redis writes:
         a. After `getOrCreate` returns the conversation object, hold it locally.
         b. After the user message append, the conversation is in Redis (this write is necessary — if Bedrock fails, we want the user message preserved).
         c. After the stream completes, the assistant appendMessage is the second write — this is also necessary.
         d. The key optimization is in `getWindowedHistory` — since we just loaded the conversation in `getOrCreate` and appended the user message, we ALREADY have the full history in the local `conversation` object. Instead of calling `getWindowedHistory(conversation.id)` (which does another Redis GET), compute the windowed history from the local object:
           ```typescript
           const history = conversation.history.slice(-12);
           ```
         e. Similarly, `getCharacterClass` and `getPronouns` can use the local conversation object instead of making separate Redis calls.
       - This reduces per-turn round-trips from ~8 to ~3 (getOrCreate=1, appendUser=1, appendAssistant=1).
